# Ecommerce builder

You do not write HTML, CSS or JavaScript. You write one file, `shop.json`. `scripts/build.py` turns it into a full shop: home, category pages with filters, product pages, search, compare, cart, checkout, order confirmation, order tracking, customer account, stores, policies, 404, and an admin dashboard. All templates, styles, scripts and product drawings already exist. Your job is to choose well and fill in correct content.

`SKILL` below means the folder that holds this file; use whichever path you loaded it from. If you cannot run shell commands, stop and tell the user: the build is required.

## Which path

Read the request and take the first row that matches.

| The user | Path |

Run lint and QA with `--sweep` on its `dist`, open the screenshots, then send one table: each problem with its kind (Broken: fails for any brand, such as overflow, low contrast, clipped text; Off-system: differs from the rest of the shop; Taste: a preference) and the fix in shop.json. Change nothing until the user picks the rows |

## What the output is

A static site that runs from a folder or any static host. Cart, wishlist, compare, accounts, orders and every admin change are kept in the browser's localStorage, so the whole flow works as a demo: place an order in the shop, open `admin/`, confirm it, and the customer's tracking page shows the new status. It is not a live store: there is no server, no payment, no shared database. `references/going-live.md` lists what a real launch needs. Say this in your report.

## The admin dashboard

`dist/admin/` is built from the same shop.json; you configure nothing except the optional `staff` list. It has an overview with a date range picker, KPI tiles and charts, orders with quick view and bulk actions, products, stock, customers, promotions, reports and settings, with keyboard shortcuts and stacked cards on phones. `references/admin.md` lists every screen and feature; read it when you describe the admin in the report.

- Data: on a demo shop the build generates about 400 days of orders, customers and website traffic with weekly rhythm and Vietnamese sales peaks, so every chart and comparison has values. On a real shop (`"demo": false`) the history is empty: the admin shows only orders placed in this browser, and traffic figures (lượt truy cập, phễu, tỷ lệ chuyển đổi) stay empty until a real backend and analytics are connected. Say which case applies in the report.
- Security: the admin password `demo` is checked in the browser. On a real shop the login page and the top bar say the admin is an unsecured preview; it must not be published before `references/going-live.md` is done.

## Rules that are never negotiable

1. Never edit files in `dist/`. Change `shop.json` and rebuild.
2. Facts come from the brief. Shop name, hotline, addresses, stores, products, prices, stock, warranty, promotions, shipping fees and payment methods must be the shop owner's. A missing contact detail becomes a placeholder in square brackets (`"[Địa chỉ trụ sở]"`) and goes in your report.
3. The build checks facts against the brief. In product specs, `highlights`, descriptions, card chips, promotions, FAQ answers, benefits, announcements, shipping times, policies and banner texts, every figure and model code (`14650HX`, `90 Wh`, `2560x1600`, `300.000`) must appear in the brief, and promises such as "chính hãng", "tặng", "miễn phí", "trả góp", "hoàn tiền", "trong ngày", "lắp đặt", "rẻ nhất" must too. Sentences copied from the example shop are errors: its facts are made up. When the brief does not give a spec, leave the row out; a short spec table from the brief is correct, a long invented one is not. Only when the user asks you to invent a whole sample shop with no catalogue of its own do you set `"sample_content": true`, which turns this check off.
4. `"demo": true` marks a sample shop: the footer and admin say the data is a sample, pages carry `noindex`, and the admin is filled with generated orders and customers. Ratings, reviews, "đã bán" counts and flash-sale "sold" numbers are only allowed on a demo shop. On a real shop (`"demo": false`) reviews must be copied word for word from the brief and the build rejects invented ones. Never set `demo` to true to get around this on a real client's shop.
5. Copy follows `references/content-rules.md`. The build fails on emoji, arrows, em or en dashes, curly quotes, banned AI words and phrases that mark text as machine-written. Fix the wording.
6. Use only the keys in `references/shop-schema.md`. Unknown keys are build errors.

## Step 1: Collect the brief

Ask one short message for anything marked * that is missing. Do not stall on the rest.

- Shop name*, hotline*, email*, working hours, head office address, legal line (company name, tax code)
- Categories they sell* and the brands in each
- Products*: name, brand, category, price in VND, old price if discounted, versions (storage, size) with their prices, colours, stock, warranty, what is in the box, main specs. A spreadsheet is fine.
- Stores (name, city, address, hours, phone) if they have any
- Shipping methods with fees and free-shipping threshold; payment methods; bank account for transfers
- Policies (warranty, returns, delivery, privacy), current promotions and voucher codes
- Logo colour (hex). Real product photos if they have them (put them next to shop.json)

If the user only wants a sample or a demo and gives no catalogue, use `examples/demo-electronics.shop.json` as the model, set `"demo": true` and `"sample_content": true`, invent a shop with fictional brands (never real brands with made-up specs or prices) and say so in the report. When the user gives a brief with products, `sample_content` stays off even on a demo: write only what the brief says.

## Step 2: Choose a style

The storefront comes in five styles. Each has its own header, homepage hero, product card, product page, listing page, footer, type and colour preset, so shops in different styles do not look alike. Pick by what the shop sells and how it sells; the admin is the same in all of them.

| Style | Pick it for | Example to copy |
|:---|:---|:---|
| `retail` | mass-market phone and electronics chains: dense cards, promotions, installment, flash sales (Thegioididong, CellphoneS) | `examples/demo-electronics.shop.json` |
| `premium` | authorised resellers of flagship models: large product pictures, few words, white space (Apple and Samsung stores) | `examples/styles/premium.shop.json` |
| `gaming` | gaming laptops, PC parts and gear: dark theme, specs first, shop by need, setup bundles (GearVN) | `examples/styles/gaming.shop.json` |
| `appliance` | TVs and home appliances for families: big category icons, shop by room, delivery and installation services (Dien May Xanh) | `examples/styles/appliance.shop.json` |
| `boutique` | accessory shops with a small curated range: collections, editorial pictures, warm calm palette | `examples/styles/boutique.shop.json` |

Set `"style"` in shop.json. To make a shop differ from another one in the same style, override parts in `"layout"`, for example `{"header": "centered", "card": "clean"}`; the parts and their variants are in `references/shop-schema.md`. When several shops sit in `sites/`, the build fails if a new one shares the style, five of the six layout parts and the preset with another, and names the variants still free. Each style's notes, with its section data shapes, are in `references/styles/<style>.md`.

### Parts, sections and a real homepage layout

- The storefront is built from 10 swappable parts (header, hero, card, pdp, plp, footer, cart, checkout, thanks, account), each with 3-7 designs, and 39 home section types with 60 extra designs. `python scripts/build.py --list` prints them with a one-line description; `references/variant-catalog.md` is the same list. Pick parts by what the brief says: a shop with one flagship line needs a different header and card than a chain with 2,000 SKUs.
- Section designs are chosen with `"variant"` on the section (`{"type": "reviews", "variant": "quotes"}`); parts with `"layout"`. Data shapes of every section are in `references/variants/*.md`.
- Follow a real homepage: set `"blueprint": "<id>"`. `python scripts/blueprints.py --style <style>` lists real shops of that kind with their section order (25 recorded in `data/blueprints/`, with the research in `docs/research/ecommerce-homepages.md` (in the job repository, not shipped with this skill)); `--show <id>` prints the order with the section types that fit each slot. The build enforces the order and at least 4 of the blueprint's roles; any slot may be left out, so a small catalogue is fine. It is required on every shop except a `sample_content` one. Do not choose a blueprint by how short it is: choose the real shop whose business is closest to the client's.

## Step 3: Start from the example

```
mkdir sites/<shop-slug>
copy the example of the chosen style (table above)  to  sites/<shop-slug>/shop.json
```

Then replace every value with the client's content:

- Put the brief, as given, in `"brief"`.
- `theme.preset`: leave it out to use the style's preset, or pick another from `references/shop-schema.md` ("Presets"); put the logo colour in `theme.accent`.
- `categories`: one per product family. `device` sets the drawn product art (phone, laptop, tablet, tv, watch, headphones, earbuds, speaker, camera, gamepad, keyboard, mouse, monitor, chair, fridge, washer, aircon, charger, powerbank). `facets` are the filters on the category page; every product in the category should give a value for each facet key.
- `products`: follow the shape in the example, but take every value from the brief. Never copy the example's specs, descriptions, promotions or `highlights`. Put prices on one option only (usually storage or configuration). Colours go in an option whose values carry `hex`. `card_specs` are the 2-3 chips on the product card. `specs` is the grouped specification table: buyers of electronics compare these, so fill it from the brief.
- `home`: list the homepage sections in order. Start from the order in the style's example. For `retail`, real Vietnamese electronics stores use: `hero`, `categories`, `flash-sale` (only with a real time-limited deal), one `rail` per main category, `banners`, `brands`, `grid`, `stores-cta`. Every section works in every style; the style examples show which ones each style leans on.
- `promotions`, `shipping`, `payments`, `benefits`, `stores`, `policies`: from the brief. `benefits` are the 3-4 promises shown in the footer and on product pages; write only promises the brief makes.

Run `python SKILL/scripts/build.py --list` for icon names, device kinds, presets and section types.

## Step 4: Build until clean

```
python SKILL/scripts/build.py sites/<slug>/shop.json --out sites/<slug>/dist
```

Every error names the JSON path and the fix. Fix shop.json and run again until it prints `OK built`. When an error says a figure is not in the brief, delete the detail (or the whole row or sentence); never add it to the brief to make the build pass. Read the WARN lines: missing facets, placeholder contacts, products without photos.

## Step 5: Lint

```
python SKILL/scripts/lint_output.py sites/<slug>/dist
```

It must print `LINT PASSED`.

## Step 6: Browser QA

```
python SKILL/scripts/qa.py sites/<slug>/dist
```

If `python` cannot import Playwright, use a Python that has it (on Windows `py -0` lists the installed versions, then for example `py -3.11`).

(`python` works too where Playwright is installed.) It opens every page at 1440 and 390 px and checks script errors, sideways scrolling, broken images, wrapped button labels and layout that moves on hover, then runs the whole flow: choose a variant, add to cart, apply a voucher, submit an empty checkout (must be stopped), fill it, place the order, track it, find it in the admin, confirm it, see "Đã xác nhận" in tracking, change a price in the admin and see it on the product page. It must print `QA PASSED`. Before delivery run it once more with `--sweep`: it narrows the main pages from 1440 to 360 px in 20 px steps and fails a page that scrolls sideways or overlaps header items at any width in between. A page whose QA fails is not finished. If a failure is in a template rather than in shop.json, quote the lines and tell the user it is a library bug. Then open `dist/qa/index-1440.png`, `index-390.png` and `admin_index-1440.png` and look at them.

## Step 7: Report

Tell the user briefly, in the language they wrote in:

- first, every choice you made for them, one line each with the reason and an offer to change it: style, blueprint, layout parts you overrode, preset, demo or real data, `sample_content`. This is the only place where you may have guessed wrong, so it goes on top
- where the site is (`sites/<slug>/dist/index.html`) and the admin (`dist/admin/login.html`, password `demo`). On a real shop (`"demo": false`) say that the admin is an unsecured preview (the password is checked in the browser and the page says so) and must not be published before `references/going-live.md` is done
- what the admin shows and whether its history is sample data or empty (see "The admin dashboard")
- how to view it: open the file, or run `python -m http.server` inside `dist`
- style, layout parts, preset, categories, number of products
- every placeholder and warning left open, and that the site is a front end with browser storage: list the items from `references/going-live.md` the client needs before taking real orders

## Reference files

- `references/shop-schema.md`: every key of shop.json, required or optional, with limits; presets; home sections
- `references/content-rules.md`: copy rules, demo versus real data, what the build checks
- `references/patterns.md`: what real electronics stores and admin panels do, with counts from the research, and where each pattern lives in the templates
- `references/styles/<style>.md`: what each of the four added styles is for, its parts, the data shapes of its sections and how it was verified
- `references/variant-contract.md`: how to add a variant or a section (first-line description, hooks, tokens-only css) and how it is checked
- `references/variant-catalog.md` (generated) and `references/variants/*.md`: every variant and the data shape of every section
- `references/going-live.md`: what a static build cannot do (payments, shared orders, live stock) and the options read from vendor docs
- `references/admin.md`: every admin screen and feature, for describing the admin in the report
- `references/maintaining.md`: adding a rule, a part or a section, and the checks to run after a change to the library
- Research behind the templates: `docs/research/ecommerce-electronics-dashboards.md`, `docs/research/ecommerce-overview-analytics.md` (overview charts and date picker) and `docs/research/ecommerce-mobbin-screens.md` (in the job repository, not shipped with this skill)

## Changing the library

Adding a rule, a variant, a section or a check, and the regression tests to run afterwards, are in `references/maintaining.md`. Read it before editing build.py, a template, a schema or this file; building a page for a client does not need it.
